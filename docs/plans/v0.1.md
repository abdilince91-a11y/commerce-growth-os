# v0.1 Implementation Plan — Commerce Growth OS

Status: DRAFT — needs sign-off before any code is written (tech stack and
schema below are proposals, not decisions).

## 1. Scope recap (from README)

In scope for v0.1:
- Canonical product schema
- Product metadata quality scoring
- Search-intent clustering
- Google Merchant feed generation layer
- Pinterest feed generation layer
- Optimization recommendation model
- Human approval gates
- Initial dashboard shell
- Tests, security rules, and CI foundations

Out of scope: automatic campaign publishing, automatic budget increases,
automatic destructive actions, autonomous bidding changes. These stay
out of scope for every future version unless a human explicitly asks to
revisit that boundary — CLAUDE.md treats them as safety boundaries, not
just a v0.1 cut line.

## 2. Why the schema comes first

Every box in the README architecture diagram reads from canonical
product data:

```
Canonical Product Data
        +--> Search Intelligence
        +--> Metadata Optimizer --> Google Merchant adapter
        |                       --> Pinterest adapter
        +--> Analytics Engine --> Recommendations --> Human Approval
```

Feed adapters, scoring, and recommendations are all derived views over
one canonical record. Building any of them before the schema is fixed
means rework once the schema settles. So the schema is v0.1's critical
path, not just another item in the list.

## 3. Proposed tech stack (needs approval)

Inferred constraints already in the repo: `.gitignore` expects `.next/`
and `dist/` output, `.env.example` has a single `DATABASE_URL`, and
`package.json` has no dependencies yet — so this is a green-field
choice, not a discovery.

| Concern | Proposal | Why |
|---|---|---|
| Language | TypeScript everywhere | one type system across schema, API, and dashboard; safest default for an approval-gated system where explainability matters |
| App framework | Next.js (App Router) | dashboard shell + API routes in one deployable, matches the `.next/` ignore already in the repo |
| Database | PostgreSQL | relational integrity for canonical product data, ad accounts, approval records; matches `DATABASE_URL` |
| ORM / migrations | Prisma | schema-as-code, generates types the rest of the app consumes directly |
| Schema validation | Zod | validates untrusted external data (Merchant/Pinterest feeds, AI output) at the boundary, per CLAUDE.md's "treat all external data as untrusted" rule |
| Tests | Vitest | fast, TS-native, works for both unit and integration tests |
| Lint/format | ESLint + TypeScript strict mode | fills the currently-stubbed `lint`/`typecheck` scripts |
| CI | GitHub Actions | run lint, typecheck, test on every PR |

If a different stack is preferred (e.g. separate backend service, a
different DB), say so before step 6 below starts — this table is the
one part of this plan meant to be argued with.

## 4. Canonical product schema (draft v0)

Minimum fields needed before any adapter or scorer can be built:

```
Product {
  id                 string   // internal canonical id, stable across platforms
  sku                string
  title              string
  description        string
  brand              string?
  gtin | mpn         string?  // at least one identifier required by Merchant
  category           string   // internal taxonomy, mapped per-platform later
  price              { amount: decimal, currency: string }
  availability       enum(in_stock, out_of_stock, preorder, backorder)
  images             string[] // URLs, canonical source of truth
  attributes         Record<string, string>  // color, size, material, etc.
  sourceUpdatedAt    datetime
  canonicalUpdatedAt datetime
}
```

Platform adapters (Google Merchant, Pinterest) map *from* this shape;
they never define fields the canonical schema doesn't have. This is an
architectural decision, not just a table shape, so it belongs in
`docs/decisions/` as an ADR before implementation — see step 6.

## 5. Human approval gate (shared primitive)

Every module that produces a recommendation (metadata change, feed
update, budget/bid suggestion) writes to a shared `Proposal` record
rather than acting directly:

```
Proposal {
  id            string
  type          enum(metadata_change, feed_update, budget_change, bid_change, ...)
  target        { entity: string, id: string }
  before        json
  after         json
  rationale     string       // required — CLAUDE.md: "every recommendation must be explainable"
  status        enum(pending, approved, rejected, applied)
  createdBy     enum(system, user)
  decidedBy     string?      // human identity, required before status leaves "pending"
  decidedAt     datetime?
}
```

Nothing transitions a `Proposal` to `applied` without a `decidedBy` set
by a human action — this is the mechanical enforcement of CLAUDE.md's
"never publish/increase budget/delete without explicit approval" rules,
so it needs to exist before any module that generates proposals does.

## 6. Milestone sequence

Each milestone produces working, tested code — not a stub.

1. **Foundation** — approve stack (§3), scaffold Next.js + TS project,
   wire up lint/typecheck/test scripts, GitHub Actions CI running all
   three on PRs.
2. **ADR: canonical schema** — write `docs/decisions/0001-canonical-product-schema.md`
   formalizing §4, get sign-off, implement as Prisma schema + Zod
   validators + unit tests.
3. **ADR: approval gate** — formalize §5 as
   `docs/decisions/0002-human-approval-gate.md`, implement `Proposal`
   model + status-transition logic + tests (including a test asserting
   the transition to `applied` is blocked without `decidedBy`).
4. **Google Merchant adapter** — canonical → Merchant feed mapping,
   read-only (fetch/validate), no push capability yet. Tests cover
   missing-identifier and malformed-input cases.
5. **Pinterest adapter** — same shape as (4) for Pinterest Catalogs.
6. **Metadata quality scoring** — rule-based scorer over canonical
   fields (missing images, short titles, missing GTIN/MPN, etc.),
   output feeds into `Proposal` records, not direct writes.
7. **Search-intent clustering** — first analytics module, consumes
   canonical data + (mocked or real, TBD) search query data.
8. **Recommendation model** — combines scoring + analytics into
   `Proposal` records; this is the first module actually exercising the
   approval gate end-to-end.
9. **Dashboard shell** — list/approve/reject `Proposal` records, view
   canonical product data. This is deliberately last: it's the
   consumer of everything above, not a blocker for it.

Steps 4 and 5 can run in parallel once step 2 lands, since both only
depend on the canonical schema, not on each other. Same for steps 6/7
relative to each other once their own inputs exist.

## 7. Definition of done (per milestone, per CLAUDE.md)

- Implementation complete
- Tests pass (`npm test`)
- Lint/typecheck pass (`npm run lint`, `npm run typecheck`)
- Independent code review done, findings resolved or documented
- Security review done for anything touching credentials, external
  input, or the approval gate
- `docs/architecture/` and `CHANGELOG.md` updated if behavior/design
  changed
